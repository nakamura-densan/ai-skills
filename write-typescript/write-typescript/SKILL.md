# Write TypeScript

以下の規則に従ってTypeScriptを実装・修正・レビューする。

## 基本

- リンターと矛盾する場合はリンターを優先する。
- 既存の類似実装は設計意図を確認して活用し、問題のある実装は踏襲しない。
- 可読性と変更容易性を優先し、不要な重複と過度な抽象化を避ける。
- 意味のある英単語で命名し、ローマ字を使用しない。

## 処理構造・関数

- メインフローを上から下へ追いやすくし、主要な分岐と副作用が見える構造にする。
- 関数を短くすることや責務の分離自体を目的に、処理を細かく切り出さない。
- 複数回使用する処理、再利用可能な処理、名前を付けると意図が明確になる業務ルール・変換、複雑な処理、独立してtestする価値がある処理は関数への抽出を検討する。
- 1回しか使わない短い処理や、単なる委譲・別名化だけのwrapperは、可読性が改善しないなら抽出しない。
- ローカル関数は可能な限り使用箇所の近くに定義する。

## 変数・状態変更

- `var`を使用しない。
- 再代入が不要な変数は`const`を使用する。処理の流れを明確にするための局所的な再代入は`let`を使用してよい。
- 引数、共有状態、外部から受け取ったobject・arrayを直接変更しない。
- 関数内で生成して所有している値の局所的なmutationは、immutableな書き方より処理意図が明確になる場合は許容する。

## 型

- `any`を使用せず、必要なら`unknown`から絞り込む。
- compilerを黙らせる目的の`as`と、非nullアサーション`!`を使用しない。
- 値の具体的な型推論を維持したまま型との整合性を検証したい場合は、型アサーションではなく`satisfies`を検討する。
- 既存の分岐やnull checkで表現できる場合、不要なユーザー定義型ガードを増やさない。
- `enum`と`interface`を使用せず、ユニオン型と`type`を使用する。
- 型名はPascalCaseとし、型推論で十分な場合は型注釈を追加しない。
- 新しい型を定義する前に、同じ概念を表す既存型がないか確認し、型情報のSingle Source of Truthを維持する。
- 既存型の一部・変形として表現できる型は同じ構造を再定義せず、必要に応じて`Pick`、`Omit`、`Partial`、`Required`、`Readonly`等のutility typeから導出する。
- 実装や既存の型情報から導出できる場合は、`typeof`、`ReturnType`、`Parameters`、indexed access type等を使用し、同じ型情報を重複して定義しない。
- 構造が同じでも、意味・責務・変更理由が異なる型は再利用目的だけで統合しない。APIの入出力、外部境界、永続化モデル、UI入力など、独立して変更される契約は必要に応じて別の型として定義する。
- utility typeの多段化によって型の意図が読みづらくなる場合は、意味のある名前を付けたtypeとして定義する。
- 相互排他的な状態や処理結果は、複数のbooleanやoptional propertyの組み合わせより、必要に応じてdiscriminated unionで表現し、不正な状態を型で表現できないようにする。
- キーが有限かつ静的な辞書には`Record`、動的なキー・非stringキー・頻繁な追加削除・`Map` APIが適する場合は`Map<K, V>`を使用する。
- 外部入力・信頼境界ではruntime validationを行う。すでに信頼境界で検証済みであることが保証されている値を、内部レイヤーで重複してvalidationしない。

## 命名

- componentと型: PascalCase
- 変数・関数・メソッド: camelCase
- hooks: `use`で始める。
- module scope等で定義する、意味上の固定定数にはUPPER_SNAKE_CASEを使用する。通常の`const`変数はcamelCaseとする。
- Boolean: 意味に応じて`is`、`has`、`can`、`should`、`exists`、`needs`等を使用する。
- 日付のみ: `Date` suffix。例: `startDate`
- 日時: `At`または`DateTime` suffix。例: `createdAt`, `startDateTime`
- 時間のみ: `Time` suffix。例: `startTime`
- 関数名は実装手段ではなく、呼び出し側から見た処理の意味を表す動詞を使用する。
- `get`、`process`、`handle`等の汎用的な名前を機械的に使用せず、`find`、`fetch`、`create`、`calculate`、`format`、`parse`等から実際の処理を最も正確に表す語を選ぶ。
- DBやAPIなどの実装詳細を関数名へ含めるかは、その違いが呼び出し側にとって意味を持つ場合に判断する。

## 制御構文

- Promiseの`.then` / `.catch`による処理の連鎖より、制御フローが明確になる`async` / `await`を優先する。
- 相互に依存しない非同期処理は不要に直列化せず、`Promise.all`等で並列性を維持する。
- 条件は可能な限り肯定形にし、早期returnでネストを浅くする。
- 範囲判定は`lower <= value && value < upper`のように、範囲の並びが視覚的に分かる形を優先する。
- `map`、`filter`、`reduce`で意図が明確になる場合は使用し、状態遷移や複数値の組み立てで読みづらくなる場合は`for...of`等を使用する。
- 三項演算子をネストせず、複雑になる場合は通常の条件分岐へ変更する。

## 例外処理

- `catch`は、エラーからの復旧、期待されるエラーへの変換、文脈情報の追加、cleanupなど、その層で処理する理由がある場合に使用する。
- 処理できない例外をcatchしてログ出力し、そのまま再throwするだけの実装は避ける。ログは原則として適切な境界で一度だけ記録する。
- catchした値は`unknown`として扱い、必要な情報を利用する前に安全に型を絞り込む。
- `try` / `catch` / `throw`を通常の分岐の代替として使用しない。
- エラーを別のエラーへ変換する場合は、`cause`等を使用して元の原因を保持する。

## 日付処理

- 日付・日時の加減算、期間計算、月初・月末などのカレンダー操作、timezone変換、parse・formatは、プロジェクトで採用しているluxon等の既存ライブラリを使用する。
- `Date#setDate`、`Date#setMonth`、`Date#setHours`等とgetterを組み合わせた日付計算を実装しない。暦・timezone・DSTを意識した処理をライブラリのAPIで明示的に表現する。
- 日、月、年など暦に依存する単位の加減算・差分計算は、ミリ秒への変換や定数除算で実装しない。
- 標準`Date`自体は禁止しない。API・DB・外部ライブラリとの受け渡し、既存の型との整合、単純な現在日時の取得など、日付計算を伴わない用途では使用してよい。
- `Date#getTime()`等による単純な日時比較やtimestampへの変換まで禁止しない。
- `Date`を受け取った場合も、日付計算が必要になった時点で既存ライブラリの型へ変換し、計算結果は必要な境界で`Date`や文字列へ戻す。

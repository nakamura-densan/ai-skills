# Tooling Audit

## 目的

AIは意味・責務・状態・依存関係などの設計判断へ集中し、コンパイラ、型検査、静的解析、テスト、スキーマ、CIなどで機械的に検出できる問題を人間や生成AIの注意力へ戻さない。

このReferenceでは技術固有のツール名や設定項目を定義しない。具体的に何を確認するかは、対象技術のReferenceへ置く。

## 確認順序

1. プロジェクトで実際に有効なコンパイラ、型検査、静的解析、リンター（linter）、フォーマッター（formatter）、テスト、スキーマ検証、CIを確認する。
2. 各仕組みが何を検出・保証し、どの範囲へ適用されているかを確認する。
3. 除外設定（ignore / override）、警告の大量放置などによって、重要な領域が実質的に未検証になっていないか確認する。
4. ローカルで実行できるだけでなく、必要な検証がCIの必須条件になっているか確認する。
5. 技術固有の設定、API、生成物、フレームワーク検証は該当するTechnology Referenceで確認する。

## 技術非依存の確認項目

### コンパイラ / 型検査

- 型や言語仕様で検出できる誤りを、コメントやレビュー規約だけで防いでいないか
- 実際のビルドで使われる設定と、エディタだけの設定が食い違っていないか
- 生成型や生成コードを使う場合、生成元とのずれをビルドやCIで検出できるか

### リンター（Linter） / フォーマッター（Formatter） / 静的解析

- 既存の解析がCIで実行されているか
- 重要なルールが対象ファイルや対象ディレクトリから除外されていないか
- 警告を大量に残した結果、新しい問題を識別しにくくなっていないか
- formatterの例外設定に明示的な理由があるか

### テスト（Test） / ビルド（Build）

- 単体、統合、E2E等の検証範囲が、実際に確認したい境界と一致しているか
- 必須テストとビルド検証がCIの必須条件になっているか
- flaky testを恒常的なretryだけで隠していないか
- 実運用で使う設定や起動経路と、テストだけの構成が離れすぎていないか

### 依存関係 / 未使用コード / アーキテクチャ

- プロジェクトで既に依存関係、未使用コード、循環依存、アーキテクチャ境界を検証する仕組みがあれば活用する
- 同じ問題を検出するためだけにSkill専用の独自スクリプトを追加しない
- 新しいツールを提案する場合は、検出できる問題と継続的な保守コストを比較する

### データ / スキーマ（Schema） / マイグレーション（Migration）

- 一意性、参照整合性、必須性、値域等をデータストア側で保証できる場合、アプリケーションの注意力だけへ任せていないか
- スキーマ変更やマイグレーションの不整合を、適用前に検出できる仕組みがあるか
- 生成された変更内容を確認せず、そのまま安全だとみなしていないか

## 指摘方針

既に機械的に担保されている問題は、原則としてFindingの主題にしない。必要なら「既存の仕組みで担保済み」と確認だけ残す。

同種の問題が繰り返し発生し、既存の仕組みで検出できる場合は、個別修正を列挙するより設定・検証経路の改善を優先する。新しいツールを追加する場合は、そのSkillを使うためだけの仕組みにせず、通常の開発・CIでも継続的に価値がある場合に限る。

意味や責務の分割、抽象化の妥当性、状態モデル、変更理由など、機械的な検出だけでは判断できない問題はAIレビューで扱う。

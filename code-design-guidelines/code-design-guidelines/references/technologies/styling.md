# スタイリング方式の判定ガイド

この参照資料（Reference）はスタイリング方式を判定するためのルーターとして使う。方式ごとの詳細な設計判断は、該当する参照資料だけを追加で読む。

## 1. 実際に使われている方式を特定する

`package.json`に依存があるだけで採用方式を決めない。次を確認する。

- 対象コンポーネント周辺の`import`
- フレームワーク / コンポーネントライブラリの設定
- ビルドプラグイン / バンドラー設定
- テーマ（Theme） / トークン（Token）定義
- 代表的なスタイル記述

判定例:

- `@emotion/react`や`@emotion/styled`をアプリケーションコードから直接利用 → [Emotion](emotion.md)
- Material UIの`sx`、`styled`、テーマ（Theme）、`components`設定を利用 → [Material UI](mui.md)
- `@vanilla-extract/css`、`recipe`、`@vanilla-extract/dynamic`等を利用 → [vanilla-extract](vanilla-extract.md)
- CSS、SCSS、CSS Modulesを主に利用 → [CSS / CSS Modules](css.md)

MUIが内部依存としてEmotionを使っているだけなら、Emotionを直接採用しているとは判断しない。MUIの公開スタイリングAPIだけを使っている場合は、まずMUIの参照資料を適用する。

## 2. 共通して確認すること

方式に関係なく、次だけを共通基準として確認する。

- 親レイアウトと子コンポーネントのどちらが配置責務を持つか
- 色、余白、タイポグラフィ等の意味的な共通値がテーマ / トークンの正本へ集約されているか
- コンポーネントの`variant` / `size` / 状態（state）とスタイル条件が別々の場所へ重複していないか
- ライブラリの公開APIで解決できるものを、生成クラス名や非公開DOM構造への依存で上書きしていないか
- 一度の局所変更のために新しいスタイリング方式を追加していないか

複数方式が併存していても、それだけを問題にしない。境界と正本が追跡できるかで判断する。

## 3. バージョン依存事項

SSR統合、テーマAPI、非推奨API、ビルド連携等が判断に影響する場合は、対象ライブラリの実バージョンと公式情報を確認する。

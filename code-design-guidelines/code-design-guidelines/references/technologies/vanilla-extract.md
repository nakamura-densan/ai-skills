# vanilla-extract設計ガイド

vanilla-extractを利用している場合、ビルド時に静的CSSを生成する設計を保ちながら、テーマ（Theme）、バリアント（variant）、実行時値の責務を分ける。

## 1. テーマ契約（Theme Contract）を意味的な正本にする

`createThemeContract` / `createTheme`等を利用している場合、同じ意味の色や余白を別の定数体系へ複製しない。

テーマ契約は「値が同じだからまとめる」のではなく、同じ意味で切り替わるトークン（token）を表すために使う。

## 2. 静的に表現できるスタイルを実行時処理へ戻さない

vanilla-extractで静的に表現できるスタイルのために、別の実行時CSS-in-JS（Runtime CSS-in-JS）を追加しない。

実行時の値が本当に必要な場合は、CSS Custom Propertiesと`assignInlineVars`等、既存の正式な仕組みで境界を局所化できないか確認する。

## 3. バリアント（variant）は`recipe`等へ意味的に集約する

`size`、`tone`、`variant`等、コンポーネントAPIとして意味を持つスタイル条件が複数箇所へ散る場合は、`recipe`等で対応表を一箇所へ集約することを検討する。

単発の条件スタイルまで`recipe`化しない。バリアント追加時に変更箇所が明確になるかで判断する。

## 4. スタイル定義の分割で探索を増やさない

ファイル分割は生成CSSの都合ではなく、コンポーネントの責務と変更理由に合わせる。

コンポーネントの見た目を理解するために複数の`.css.ts`を往復する構造になっていないか確認する。小さなコンポーネントの局所スタイルまで過剰に分割しない。

## 5. 機械的な検証・設定をビルド時CSS生成へ合わせる

vanilla-extractはビルド時変換へ依存するため、型検査だけでなく実際のビルド連携を確認する。

- フレームワーク / バンドラー（bundler）向けプラグインが対象環境で有効になっているか確認する
- Theme Contract、`recipe`、`assignInlineVars`等の型検査で検出できる不整合はTypeScriptへ任せる
- CIで実ビルドを通し、CSS生成・import解決・SSR等の統合不備を検出する
- 設定方法やプラグインAPIは利用frameworkとvanilla-extractのバージョンで変わり得るため、対象版の公式情報を確認する

設定追加そのものを改善とせず、実際の生成CSSや型契約を機械的に確認できる状態を優先する。

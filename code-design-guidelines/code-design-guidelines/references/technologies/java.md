# Java設計ガイド

Javaでは、Coreの原則を「型階層、コンパイラ、例外モデル、オブジェクト同一性、リソース管理、並行実行モデルで、誤った状態や変更漏れを検出しやすくする」方向へ具体化する。

最初に実際のJavaバージョン、`--release` / ツールチェーン（toolchain）、プレビュー機能（Preview feature）の有効化有無を確認する。利用可否や正式提供状況が版に依存する言語機能は [Version Awareness（バージョン依存事項）](../core/version-awareness.md) に従う。

## 1. 閉じた種類集合は型階層と網羅性で表現する

業務上「種類が列挙でき、その追加時に全処理を見直したい」概念では、対象Javaバージョンで利用できる場合、`sealed`型と`switch`の網羅性を使って変更漏れをコンパイル時へ寄せる。

- 任意の拡張を許す必要がないドメイン分類では、`sealed interface` / `sealed class`を候補にする
- 分岐側は、種類追加時に未対応箇所が明らかになる形を優先する
- 将来第三者が実装を追加する公開拡張ポイントへ、閉じた型階層を機械的に適用しない
- `default`で未知の種類を握りつぶすと、型追加時の検出機会を失わないか確認する

`sealed`型の拡張や網羅的`switch`の挙動は、コンパイル対象と既存バイナリの組み合わせでも変わり得る。ライブラリ境界の互換性まで保証するとみなさない。

## 2. `record`は値データの契約として使う

`record`は、構成要素がそのまま値の意味を表すデータに使う。単にボイラープレートを減らす目的で、ライフサイクルや可変状態を持つオブジェクトへ適用しない。

確認する。

- DTO、コマンド、値オブジェクト等で、構成要素が値の同一性を表しているか
- `equals` / `hashCode`が全構成要素に基づくことが用途と一致するか
- `record`自体が変更不能でも、構成要素が`List`等の可変オブジェクトなら内部まで不変になるわけではないことを考慮しているか
- フレームワークがコンストラクタ、継承、プロキシ等へ要求を持つ型へ、`record`を機械的に使っていないか

## 3. `null`を契約の曖昧さとして残さない

Javaの参照型は型宣言だけでは`null`を排除しない。`null`が意味を持つ境界を明示し、内部へ無制限に伝播させない。

- 戻り値が「存在しない可能性」を表す場合、プロジェクト規約に合えば`Optional<T>`を利用する
- `Optional`をフィールド、DTO、引数へ広げる場合は、フレームワーク互換性と既存規約を確認する
- `Optional#get()`を事前確認なしで呼ぶ構造より、`orElseThrow`、`map`、`flatMap`等で存在しない場合の扱いを契約へ含める
- null許容性アノテーション（nullability annotation）や静的解析を既に採用している場合は、その契約を崩さない
- 「ここでは必ず非null」という前提をコメントだけへ置かず、生成経路や検証で保証できないか確認する

## 4. ジェネリクスの型安全性を途中で失わない

生の型（raw type）や広域な未検査キャスト（unchecked cast）は、その地点から先の型保証を弱める。

- `List`ではなく`List<T>`のように型引数を保持する
- 外部ライブラリや反射API等で未検査キャストが避けられない場合は、検証可能な小さな境界へ閉じ込める
- `@SuppressWarnings("unchecked")`をクラス全体へ付けず、必要な箇所へ限定する
- APIの入出力でワイルドカード（wildcard）を使う場合は、読み取り専用・書き込み可能など実際の変性（variance）要件に対応しているか確認する
- 複雑な型パラメータで利用側の理解コストが上がる場合は、型安全性によって防げる具体的な誤用と比較する

## 5. `equals` / `hashCode`とコレクションキーの安定性を守る

`HashMap`、`HashSet`等は`equals` / `hashCode`の契約へ依存する。キーとして使った後に比較結果へ影響する状態が変わる設計は避ける。

- 値オブジェクトの同一性を手書きする場合、`equals`と`hashCode`を同じ構成要素から導く
- 可変フィールドをハッシュキーの同一性へ含める場合、登録後の変更で検索不能にならないか確認する
- エンティティ識別子と値オブジェクトの値同一性を混同しない
- 配列を値として比較する場合など、Java標準の`equals`挙動が意図と一致するか確認する

## 6. 例外はJavaの伝播・ロールバック契約を壊さず扱う

例外を捕捉する地点は、その例外を回復・変換・境界契約へ変換できる場所にする。

- `catch (Exception)`で握りつぶし、成功相当の値へ変換しない
- 別例外へ変換する場合は、診断に必要な原因（cause）を失わない
- 検査例外（checked exception）と非検査例外（unchecked exception）の使い分けは、呼び出し側に何を強制したいかとフレームワークの挙動を確認する
- 例外を通常の分岐制御として大量に利用しない
- `AutoCloseable`なリソースは原則`try-with-resources`で寿命をコード構造へ結び付ける

Spring等のトランザクションや非同期実行では、例外種別がフレームワークのロールバック・通知挙動へ影響するため、該当技術Referenceも確認する。

## 7. 共有可変状態と並行実行を明示する

複数スレッドから触れる可能性があるオブジェクトでは、可変状態が共有されるかを先に確認する。

- 単なる`ArrayList`、`HashMap`、可変フィールドを複数スレッドから更新する設計にしない
- 原子的な単一値には`Atomic*`、共有コレクションには`java.util.concurrent`の型、複数状態の不変条件にはロック等、守る単位に合う仕組みを選ぶ
- `parallelStream()`を性能改善の既定手段にせず、共通の`ForkJoinPool`、ブロッキング処理、副作用、順序要件を確認する
- 仮想スレッド（virtual thread）を利用する場合も、DBコネクション、HTTPコネクション、外部API等の有限資源が無制限になるわけではない
- `ThreadLocal`へ置いた文脈が非同期境界や実行方式変更で期待通り伝播するとは仮定しない

並行処理APIや仮想スレッド（virtual thread）の利用可否・推奨設定は対象Javaバージョンと実行環境を確認する。

## 8. 日時は`java.time`を正本にする

新規の日時計算では、特別な互換理由がなければ`java.time`を使う。

- 絶対時刻は`Instant`、タイムゾーン付き日時は`ZonedDateTime`等、意味に合う型を選ぶ
- `LocalDateTime`へタイムゾーンの意味を暗黙に持たせない
- `Date` / `Calendar`が外部API境界で必要な場合は、変換を境界へ局所化する
- `Instant.now()`等へ直接依存するとテストしにくい処理では、プロジェクト規約に沿って`Clock`を注入し、現在時刻を制御可能にできないか確認する

## 9. 機械的な検証・設定をJavaのコンパイルモデルへ合わせる

- 実JDK、`--release`、Maven / Gradleのツールチェーン（toolchain）等を確認し、開発環境とCIで異なるJava仕様を前提にしていないか確認する
- コンパイラ警告（compiler warning）や、既に採用しているCheckstyle / PMD / SpotBugs / Error Prone等の静的解析を、Java APIの誤用・未検査操作・規約違反の検出へ活用する
- ArchUnit等のアーキテクチャテストを既に採用している場合、依存方向やパッケージ（package）境界の機械検証へ利用する
- 既存のコンパイラ / 静的解析 / テストで確実に検出できる問題を、AIレビューの主Findingとして重複させない

新しい解析ツールは、繰り返し発生する問題を通常のビルド / CIで継続的に検出できる場合に限って検討する。

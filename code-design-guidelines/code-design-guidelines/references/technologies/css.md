# CSS / CSS Modules設計ガイド

CSS、SCSS、CSS Modules等を直接利用している場合、カスケード、詳細度、適用範囲、CSS Custom Properties（CSSカスタムプロパティ）を具体的に確認する。

## 1. 適用範囲をコンポーネント境界へ合わせる

コンポーネント固有スタイルを広いグローバルセレクターへ置かない。

- CSS Modules等で局所化できるスタイルがグローバルへ漏れていないか
- 親コンポーネントが子孫の内部DOM構造へ深いセレクターで依存していないか
- DOM構造変更で無関係なスタイルまで壊れないか

グローバルCSSはリセット（reset）、基本タイポグラフィ、アプリ全体で共有する要素規則など、実際にグローバルである責務へ限定する。

## 2. 詳細度の競合を構造で解消する

`!important`、過度に深いセレクター、同じプロパティの打ち消し合いが増えている場合は、詳細度を上げ続ける前にスタイルの所有場所を見直す。

- 親レイアウトが決めるべき配置を子で相殺していないか
- 修飾クラス（modifier） / 状態クラス（state class）の優先関係が偶然の読み込み順へ依存していないか
- 同じコンポーネントへ複数のスタイル源が競合していないか

## 3. CSS Custom Properties（CSSカスタムプロパティ）を意味的トークン（semantic token）として使う

CSS Custom Propertiesを単なる値の短縮名として増やさない。

- 同じ意味で複数箇所から参照される値か
- テーマ（Theme）切替や親スコープからの上書きが設計上必要か
- 名前から用途と所有責任を判断できるか

値が偶然同じだけなら一つの変数へ統合しない。

## 4. CSS Modulesでも内部構造への依存を増やさない

クラス名が局所化されても、コンポーネント責務が自動的に分離されるわけではない。

親から子コンポーネント内部のクラス構造へ依存したり、`composes`等で依存関係を複雑にしたりする場合は、局所理解と変更影響を確認する。

## 5. ブラウザー・フレームワーク依存機能は実環境で確認する

新しいCSS機能、CSS Modules仕様、フレームワークの読み込み順や最適化が判断に影響する場合は、対象ブラウザー・フレームワーク・バージョンを確認する。

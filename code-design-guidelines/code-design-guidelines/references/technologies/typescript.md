# TypeScript設計ガイド

TypeScriptでは、Coreの原則を「型システムとコンパイラで、誤った実装や変更漏れを表面化させる」方向へ具体化する。

## 1. 外部境界では実行時検証を行う

TypeScriptの型は実行時には入力を検証しない。HTTP、JSON、`FormData`、環境変数、外部SDKなど、実行時に外部から入る値は型注釈だけで信用しない。

- 境界では`unknown`として受け、Zod等の実行時スキーマや明示的な検証で型付き領域へ入れる
- 型アサーション（`as`）だけで外部データを内部型へ変換しない
- 検証ルールと型が同じ契約を表す場合は、スキーマから型を導出するなど正本を一つにする
- 内部ロジックは、検証済みの型を前提にして毎回再検証しない

## 2. 区分追加時の変更漏れをコンパイラへ出す

状態や種類が増える設計では、追加時に未対応箇所がコンパイルエラーとして現れる構造を優先する。

- 判別可能ユニオン（discriminated union）で状態ごとの必要情報を表す
- `switch`等では`never`を使った網羅性チェック（exhaustive checking）を検討する
- 種類ごとの処理表では、`satisfies Record<Kind, Handler>`等でキーの網羅性を検証する
- 将来の区分追加を握りつぶす`default`や広すぎる`string`型が、変更漏れを隠していないか確認する

単にユニオン型を使うのではなく、区分追加時に「どこを直すべきか」がコンパイラから分かる構造になっているかを見る。

## 3. 不可能状態を型で表現しにくくする

複数の`boolean`や省略可能プロパティで、一緒には成立しない状態を同時に表現できる場合は、状態モデルを見直す。

- `isLoading`、`isSuccess`、`isError`のような独立した真偽値より、必要に応じて状態ごとのユニオンを使う
- 状態ごとに必要な値を同じ型の省略可能プロパティへ集めすぎない
- ID、金額、期間など、取り違えが実害につながる概念はプロジェクト規約に沿って意味のある型で表せないか検討する

型を細分化すること自体は目的にしない。誤った組み合わせや取り違えを実際に防げる場合に使う。

## 4. 型の正本を一つにする

同じドメイン概念や契約を複数箇所で独立して定義しない。

優先する手段:

- 既存型から`Pick`、`Omit`、`Partial`、`Required`、インデックスアクセス型（indexed access）等で必要な形を導出する
- 関数契約から`ReturnType`、`Parameters`等を利用できる場合は再定義しない
- OpenAPI、実行時スキーマ、Prisma等が正本なら、コード生成や型導出を利用する

構造が同じだけで変更理由が異なるDTOやモデルは共通化しない。型再利用のために多段の条件型や複雑なジェネリクスが必要になる場合は、局所理解のコストと比較する。

## 5. 型安全性の逃げ道を局所化する

### `any`

通常は避ける。`any`が広がると、その先で型検査が機能しなくなる。

外部データや型不明値は`unknown`から絞り込む。既存ライブラリの型不備などで必要な場合は、境界の小さな範囲へ閉じ込める。

### `as`

型アサーションは実行時保証を増やさない。検証、型ガード、API設計で表現できる場合はそちらを優先する。

### 非nullアサーション `!`

「必ず存在する」条件が型や制御フローから読み取れないまま`!`へ依存している場合は、初期化順序やデータモデルの問題を疑う。

`as const`など、型を狭めるための別用途とは区別する。

## 6. コンパイラ設定を品質機構として扱う

`tsconfig`の実設定を確認し、プロジェクトが有効にしている型検査を前提に設計する。

`strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`等を提案する場合は、設定を強くすること自体を目的にしない。どの不具合を機械検出できるかと、既存コードへの移行コストを示す。

設定項目の意味や利用可否がバージョンに依存する場合は、[Version Awareness（バージョン依存事項）](../core/version-awareness.md) に従う。

## 7. 日付計算はプロジェクト標準へ寄せる

日付の加減算、タイムゾーン変換、期間判定を`Date`のミリ秒計算や独自処理で散らさない。プロジェクトがLuxon等を標準採用している場合は、そのライブラリへ統一する。

外部APIやライブラリ境界で`Date`が必要な場合まで禁止しない。変換を境界へ局所化し、内部の日付操作方法を複数持たない。

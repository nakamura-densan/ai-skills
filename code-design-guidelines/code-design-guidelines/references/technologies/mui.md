# Material UI設計ガイド

Material UIの公開スタイリングAPIを利用している場合に適用する。内部でEmotionを使っているという理由だけでEmotionの設計を直接要求しない。

## 1. 適用範囲に合うカスタマイズ手段を選ぶ

スタイルの影響範囲と所有責任を合わせる。

- その場の1インスタンスだけの調整 → `sx`等の局所手段
- 再利用される独自コンポーネント → `styled`や共通コンポーネント化を候補にする
- アプリ全体で同じMUIコンポーネントへ適用 → テーマ（Theme）の`components` / `styleOverrides`
- コンポーネントAPIとして意味のある見た目の種類 → テーマの`variants`等を候補にする

一度しか使わないスタイルをテーマへ上げたり、全画面共通ルールを各`sx`へ複製したりしない。

## 2. テーマ（Theme）を意味的な正本として使う

`palette`、`spacing`、`typography`等で既に表現されている意味を、別の定数体系へ複製しない。

独自のバリアント（variant）やトークン（token）を追加する場合は、複数箇所で同じ意味として利用され、変更理由も共通かを確認する。

TypeScriptで独自バリアント等を公開APIに追加する場合は、必要に応じてモジュール拡張（module augmentation）で型にも反映し、文字列だけが先行しないようにする。

## 3. 生成クラス名へ依存しない

DOM上に現れるハッシュ（hash）付きクラス名など、不安定な生成クラスをセレクターとして利用しない。

MUIが公開しているスロット（slot）用のグローバルクラス、`sx`、テーマ上書き、コンポーネントAPI等で表現できないか確認する。

非公開DOM構造へ深いセレクターで依存する場合も、MUIの更新で壊れる境界として扱う。

## 4. `sx`の重複を意味で判断する

複数の`sx`が似ているだけで共通化しない。同じ意味・同じ変更理由のスタイルが複数箇所へ繰り返される場合に、テーマ、バリアント、共通コンポーネントへの集約を検討する。

逆に、呼び出し側固有のレイアウト調整まで共通コンポーネント内部へ吸収しない。

## 5. バージョン依存APIを固定しない

`styleOverrides`、`variants`、スロットAPI、非推奨クラス、SSR連携等はバージョンで変わり得る。対象プロジェクトのMUIバージョンを確認し、公式情報に基づいて判断する。

# React設計ガイド

Reactでは、Coreの原則を「状態の所有場所、状態遷移、レンダリング、Effect（外部同期処理）、コンポーネントの同一性（Identity）」へ具体化する。

## 1. 状態の正本を一つにする

同じ情報を複数の状態へ保存し、同期処理で整合性を保つ構造を避ける。

- `props`や既存の状態（state）からレンダリング時に計算できる値は、原則として状態へ保存しない
- 選択対象をオブジェクト全体とIDの両方で保持するなど、同じ事実を二重管理しない
- 常に同時に変化する状態は一つの状態としてまとめられないか確認する
- 一方だけ変更できる必要がある値を、近くにあるという理由だけで一つのオブジェクトへまとめない
- 親と子で同じ状態を持つ場合は、どちらが正本かを明確にする

## 2. 不可能な状態を作りにくい形にする

`isLoading`、`isSuccess`、`isError`のような独立した状態が矛盾し得る場合は、状態遷移を一つのモデルとして表現する。

状態遷移が多数のイベントハンドラーへ散り、同じ状態群を複数箇所で更新している場合は`useReducer`を候補にする。

`useReducer`は状態が多いから使うのではなく、次の条件で価値を判断する。

- 同じ状態への遷移ルールが複数箇所へ散っている
- イベントごとの更新条件を一箇所で確認したい
- アクション（Action）追加時に更新規則を追跡しやすくしたい

単純な`useState`まで機械的に状態遷移関数（Reducer）へ置き換えない。

## 3. ユーザー操作とEffect（外部同期処理）を分ける

ユーザー操作によって発生する処理はイベントハンドラーへ置き、レンダリング結果として外部システムと同期する処理にEffectを使う。

問題候補:

- `props` / 状態から派生値を作るためだけのEffect
- クリック等の明確なユーザー操作をEffect経由で実行する
- 状態A変更 → Effect → 状態B変更という同期鎖
- 依存配列を意図的に欠落させないと成立しないEffect
- 接続には切断、購読には解除が対応していないEffect

Effectの依存関係は「実行回数を調整するために選ぶ値」ではなく、Effect内部で参照するリアクティブ値から決まる。依存を減らしたい場合は、依存配列を抑制する前にEffectの責務やコード配置を見直す。

## 4. コンポーネントの同一性（Identity）で状態寿命を設計する

Reactの状態（state）はレンダーツリー上の位置に結び付く。対象が切り替わった際に内部状態を初期化したい場合、Effectで複数の状態を手動リセットする前に、コンポーネントの同一性や`key`で状態寿命を表現できないか確認する。

- 別の業務対象なのに同じコンポーネントとして状態を引き継いでいないか
- 同じ対象なのに毎回`key`が変わって不要に状態を失っていないか
- 状態初期化のためだけのEffectが増えていないか

## 5. Custom Hook（カスタムフック）は振る舞いの境界として切り出す

「状態を持つからCustom Hook（カスタムフック）」「状態を持たないからユーティリティ」という分類は行わない。

カスタムフック（Custom Hook）は、次のようなReact固有の振る舞いを意味のある操作として隠せる場合に使う。

- 外部システムとの接続・購読・解除
- 複数の状態とEffectで構成される一つの状態プロトコル
- 複数コンポーネントで共有するReact依存ロジック

`useMount`、`useEffectOnce`のようにライフサイクルだけを別名で包み、依存関係や同期対象を見えにくくしない。フック名は「何をするか」を表す。

カスタムフックはロジックを共有するが、呼び出し元同士で状態そのものを共有するわけではない点も区別する。

## 6. コンポーネント分割は所有責任で判断する

分割は次のいずれかが得られる場合に行う。

- 独立した表示・状態・イベントの責務がある
- 異なる理由で変更される部分を分離できる
- 再利用されるUI単位として契約が明確になる
- 親コンポーネントの主処理を追いやすくできる

数行の補助表示まで必ず別ファイルへ出さない。小さな補助コンポーネントを同一ファイルに置く方が局所理解しやすい場合はそのままにする。

## 7. メモ化は性能機構として扱う

`useMemo`、`useCallback`、`memo`は正しさを成立させるために使わない。

- Effectの依存を安定させるためだけにメモ化を重ねていないか
- 実際の再計算・再レンダリングコストに対して複雑性が見合うか
- プロジェクトがReact Compiler（Reactコンパイラ）等の自動最適化を利用している場合、その実設定を確認しているか

推奨方法や自動最適化の提供状況がバージョンに依存する場合は、[Version Awareness（バージョン依存事項）](../core/version-awareness.md) に従う。

## 8. 検証単位をReactの境界に合わせる

状態遷移や業務計算を純粋ロジックとして分離できる場合は小さくテストする。一方、DOM、イベント、Effect、Context（コンテキスト）等のReact固有の振る舞いは、内部実装をモックするよりコンポーネントとして検証する。

「テストしやすくするため」だけにHook、Context（コンテキスト）、Interface（インターフェース）等を追加しない。

## 9. 機械的な検証・設定をReactの実行モデルへ合わせる

- `eslint-plugin-react-hooks`等を採用している場合、フックのルール（Rules of Hooks）やEffect依存関係を静的解析で検出し、`eslint-disable`で恒常的に回避していないか確認する
- React Compilerを利用している場合、コンパイラ診断と既存のリンター（lint）設定を確認し、手動メモ化の追加を既定解にしない
- DOM、イベント、Effect、Context等のReact固有挙動は、採用済みのコンポーネントテスト環境で実際の利用経路を検証する
- 型検査やReact向け静的解析で確実に検出できる問題を、AIレビューの主Findingとして重複させない

React Compilerやlintルールの提供状況はバージョンで変わり得るため、対象ReactとToolingの実設定を確認する。

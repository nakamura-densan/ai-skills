# Emotion設計ガイド

Emotionをアプリケーションコードから直接利用している場合に適用する。MUIの内部スタイルエンジンとして存在するだけなら、このReference（参照資料）を機械的に適用しない。

## テーマ（Theme）の正本を`ThemeProvider`へ寄せる

アプリ全体で意味を共有する色、余白、タイポグラフィ等は、既存のテーマへ寄せる。

- コンポーネントごとに同じ意味の定数を再定義しない
- `css` / `styled`内でテーマから取得できる値を直接ハードコードしない
- テーマ更新によって連動して変わるべき値と、コンポーネント固有値を区別する

## `css`と`styled`の使い分け責務をプロジェクト内で予測可能にする

どちらか一方を常に正しいとはしない。既存規約を優先しつつ、次を確認する。

- 一度だけの局所スタイルのために不要なスタイル付きコンポーネント（Styled Component）を増やしていないか
- 再利用される意味的なコンポーネントなのに、呼び出し側ごとに同じ`css`を複製していないか
- スタイルだけを分離した結果、コンポーネントの見た目を理解するための探索が増えていないか

## 動的スタイルは入力との対応を明確にする

`props`や状態（state）からスタイルを変える場合、どの入力がどの見た目へ対応するかを追跡できる構造にする。

複数の真偽値（boolean）で組み合わせ爆発を作るより、コンポーネントのバリアント（variant）等の意味的なAPIへ寄せられないか確認する。

## SSR / キャッシュ（Cache）設定は実構成で確認する

EmotionのSSR方式、キャッシュ（Cache）、スタイル挿入順はフレームワークやEmotionバージョンとの組み合わせで変わる。

- SSR / ハイドレーション（hydration）の不具合を一般論だけで推測しない
- キャッシュや挿入順を変更する場合は、既存フレームワーク連携と公式手順を確認する
- SSR方式の違いがセレクター等へ影響する場合は、実際の方式を特定してから判断する

時点依存の統合方法をこのSkillへ固定しない。

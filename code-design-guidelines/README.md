# code-design-guidelines
コードの**保守性を高く保つための設計基準**を提供するAI Skillです。
新規実装、機能追加、修正、リファクタリングでは、生成AIがこのSkillの基準を参照して実装方針やコード構造を判断します。コードレビューにも同じ基準を利用できます。

## 目的
人間と生成AIの双方にとって、将来も安全に理解・変更・検証できるコードを維持することを目的としています。
保守性を主に次の4軸で評価します。

- **Understandability（理解容易性）**  
  意図・状態・処理の流れを、必要以上に多くのコードを追わずに理解できるか。

- **Changeability（変更・拡張容易性）**  
  変更箇所と影響範囲を特定でき、安全に変更・拡張できるか。

- **Verifiability（検証容易性）**  
  変更した処理を小さな範囲でテスト・診断できるか。

- **Simplicity（単純性）**  
  不要な状態・依存・抽象化・レイヤーを増やさず、必要十分な構造になっているか。

単に設計パターンや一般的なベストプラクティスへ合わせるのではなく、プロジェクトの既存設計・制約・Toolingを確認したうえで判断します。

## 利用方法

### コード実装
新規実装、機能追加、修正、リファクタリングでは、実装前に必要なプロジェクト情報を確認し、設計基準を実装方針へ反映します。
この場合、レビュー用レポートは生成しません。

### 設計相談
責務分割、状態管理、依存関係、API設計、抽象化などについて、保守性の観点から設計方針を判断します。

### コードレビュー
既存コードやGit差分を設計基準に沿って確認し、具体的な根拠と修正案を含むレポートを生成します。
レポートは次の場所へ保存します。

```text
.code-design/
└── reports/
    └── YYYYMMDD-HHMMSS-<target>/
        └── report.md
```

レビューのみの依頼ではコードを変更しません。

## 主な確認項目
責務、依存関係、状態、不変条件、副作用、トランザクション、失敗時安全性、診断容易性、契約、型、テスト容易性、抽象化などを確認します。
品質を実装者の注意や記憶だけに依存させず、型、API設計、責務境界、テスト、静的解析、CIなどによって正しい実装へ導ける構造を優先します。

## 対応技術

技術固有の設計基準として、現在は主に次を扱います。

- TypeScript
- React
- Next.js
- Prisma
- Styling
  - Emotion
  - Material UI
  - vanilla-extract
  - CSS Modules など

実際のプロジェクトで利用している技術・バージョン・設定を確認し、必要な基準だけを適用します。
